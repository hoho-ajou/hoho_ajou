TL;DR

5줄 요약

  • AI 에이전트(LangChain·MCP 등)는 외부 라이브러리·도구에 강하게 의존한다 → 의존성 자체가 공격 표면
  • 대표 공격 유형: 타이포스쿼팅(이름 비슷한 가짜 패키지), 악성 메인테이너 침투(xz-utils처럼 신뢰를 쌓은 뒤 배신), AI 모델 파일 자체의 악성코드
  • 업계 표준 해법은 SBOM(부품 명세서) 생성 → SCA(구성요소 분석) → 취약점 매칭 3단계 (Syft, Snyk, Dependabot 등)
  • 우리 팀의 차별점: 여기에 AI 에이전트의 권한 그래프를 더해 "그 취약점이 실제로 에이전트의 어떤 권한과 연결되는가"까지 본다 (CNAPP의 공격경로 분석 방법론을 AI 에이전트에 적용)
  • Dependency Collector는 이 파이프라인의 입구: 코드에서 의존성을 뽑고, PyPI API로 메타데이터를 채우고, SBOM을 만드는 모듈

🔵 Dependency Collector — 담당: A(총괄)

산출물: SBOM, 의존성 목록, 자산 데이터 모델

무엇을 하는가. AI 에이전트 프로젝트의 소스코드를 스캔해서 (1) 의존성 목록, (2) 외부 연동 도구(LangChain·MCP 등), (3) PyPI 메타데이터·취약점을 자동으로 뽑아내는 모듈입니다. 이 파이프라인의 입구 역할이라, 여기서 뭔가 빠뜨리면 뒤의 Risk Analyzer·ML·Attack Path Engine 전부가 그 빠진 자산을 못 보게 됩니다.

의존성을 뽑아내는 두 가지 방식

매니페스트(requirements.txt, package.json)를 그냥 파싱하는 방법과, 코드에 실제로 import된 것만 스캔하는 방법이 있습니다. requirements-parser·dparse는 전자, pipreqs는 후자입니다. AI 에이전트 오픈소스 프로젝트는 requirements.txt가 부실한 경우가 많아서, pipreqs로 실제 임포트를 먼저 스캔하고 기존 requirements.txt와 --diff로 비교하면 "선언은 안 됐지만 실제로 쓰이는" 숨은 의존성까지 잡아낼 수 있습니다.

PyPI API로 메타데이터 + 취약점 한 번에 가져오기

# 이 한 번의 호출로 최신버전·해시·취약점(OSV 링크 포함)까지 다 나옴
GET https://pypi.org/pypi/<패키지명>/json

더 정밀한 취약점 조회가 필요하면 OSV API를 직접 호출합니다:

curl -X POST https://api.osv.dev/v1/query \
  -H "Content-Type: application/json" \
  -d '{"package": {"name": "flask", "ecosystem": "PyPI"}, "version": "2.0.1"}'

SBOM 생성

pip install cyclonedx-bom
cyclonedx-py requirements requirements.txt -o sbom.json   # CycloneDX 포맷

또는 Syft를 서브프로세스로 호출해도 됩니다(컨테이너·다국어 프로젝트까지 지원): syft <경로> -o cyclonedx-json > sbom.json

🟢 Risk Analyzer — 담당: 위험분석

산출물: 위험도 점수화 로직, 정적 필터링 규칙

무엇을 하는가. Collector가 넘겨준 의존성 목록에서 위험 신호(타이포스쿼팅, 관리중단, 알려진 취약점 등)를 규칙 기반으로 찾아내고, 여기에 "그 패키지를 쓰는 에이전트가 어떤 권한을 가졌는지"를 곱해서 최종 위험도 점수를 매깁니다. 패키지 위험도 × 에이전트 권한 = 위험도 점수가 이 모듈의 핵심 공식이고, 점수 체계 설계에는 업계 표준인 CVSS(0~10점 심각도 지표)를 참고합니다.

타이포스쿼팅이란 인기 패키지와 이름이 한두 글자 다른 가짜 패키지를 올려 오타로 설치를 유도하는 공격입니다(예: requests → requets). 일반 피싱과 달리 개발자·DevOps 파이프라인을 직접 노립니다. Risk Analyzer의 "이름 유사도 기반 탐지" 규칙이 정확히 이 유형을 겨냥합니다.

🟡 ML 이상탐지 — 담당: ML탐지

산출물: 이상탐지·분류 모델, 특징 전처리 데이터셋

무엇을 하는가. Risk Analyzer의 규칙 기반 탐지는 "알려진 패턴"만 잡습니다. 신규·변종 위험 패키지처럼 규칙에 없는 위협은 정상/악성 패키지의 메타데이터·행동적 특징(feature)을 학습한 분류 모델(랜덤포레스트 등)로 잡아냅니다.

규칙 기반 vs ML 기반 비교로 이해하기 — Dependabot(규칙/DB 매칭 방식)과 Snyk(자체 DB + reachability 분석)의 차이를 보면 감이 옵니다. Dependabot은 "이미 알려진 취약점 DB에 있는가"만 확인하고, Snyk는 여기에 "실제로 그 취약한 함수가 호출되는가"까지 봐서 노이즈를 줄입니다. 우리 ML 이상탐지는 한 걸음 더 나가서 "아직 DB에 없는 패턴"까지 통계적으로 잡으려는 시도입니다 — Socket.dev의 "설치 전 행동 분석" 접근과 목적이 가장 비슷합니다.

참고 수치: JFrog 2026 리포트에 따르면 2025년 악성 npm 패키지가 451% 급증(17만개 이상)했고, 공개 레지스트리에서 500개 가까운 악성 AI 모델이 발견됐습니다. 신규 CVE는 4.8만 건 공시됐지만 "Critical" 중 실제 악용 가능한 건 12%뿐이라 — 그냥 나열이 아니라 우선순위화·이상탐지가 왜 필요한지 보여주는 수치입니다.

🟣 Attack Path Engine — 담당: 공격경로/시각화

산출물: 공격경로 그래프, 침해 시나리오

무엇을 하는가. Risk Analyzer의 위험 점수와 ML의 이상탐지 결과를 받아서, "의존성 → 에이전트 → 권한 → 공격경로"를 하나의 그래프로 연결합니다. 이 방법론은 클라우드 보안 업계의 CNAPP(공격경로 분석)을 그대로 빌려온 것입니다.

공격경로 분석의 4단계 (Wiz 방법론)

  1. 자산·위험 발견 — 리소스, 권한, 취약점, 노출된 시크릿을 전부 스캔
  2. 그래프 매핑 — 발견한 위험들을 그래프로 연결 (예: "공개 IP를 가진 서버 + 고위험 취약점"이 "과도한 권한을 가진 계정"과 연결됨)
  3. 경로 식별 — 여러 개의 낮은 위험이 연쇄적으로 이어져 심각한 경로("toxic combination")가 되는지 탐색
  4. 우선순위화 — 핵심 자산으로 이어지는 경로를 최우선으로 표시

핵심은 "개별 취약점 하나"가 아니라 "취약점들이 사슬처럼 연결된 경로"가 진짜 위험하다는 관점입니다. 단일 스캔 결과 수천 건 중 실제로 연결되어 악용 가능한 건 소수인데, 이걸 걸러내는 게 이 모듈의 존재 이유입니다.

개념을 구분하기

공격경로 vs 공격벡터 vs 공격표면

공격벡터는 공격자가 들어오는 최초 입구(피싱, 미패치 소프트웨어 등). 공격표면은 노출된 진입점 전체의 총합. 공격경로는 일단 들어온 공격자가 핵심 자산까지 도달하는 전체 이동 경로입니다. 벡터가 문이라면, 표면은 그 건물에 있는 모든 문과 창문, 경로는 문을 열고 들어온 다음 금고까지 가는 구체적인 동선입니다.

무엇을 하는가. Attack Path Engine이 만든 그래프(JSON)를 D3.js·Cytoscape.js 같은 라이브러리로 사람이 볼 수 있게 그려주는 모듈입니다. 최종적으로 지도교수·쿤텍 자문단이 결과를 판단하는 창구이기 때문에, "얼마나 알아보기 쉬운가"가 이 프로젝트 전체의 설득력을 좌우합니다.

사례로 이해하기

실제 공급망 공격 3가지

사례 1 · 가장 단순한 유형

colorama / colorizr 타이포스쿼팅

PyPI의 colorama와 NPM의 colorizr 이름을 헷갈리게 만든 가짜 패키지들. Windows에서는 레지스트리에서 환경변수를 탈취하고 작업 스케줄러로 지속성을 확보하며 백신을 회피, Linux에서는 RSA 키를 배포하고 gs-netcat으로 암호화된 역쉘을 열어 Pastebin으로 데이터를 유출. 패키지 소유자 계정명, 파일 해시까지 실제로 공개된 분석 사례입니다.

사례 2 · 역사상 가장 정교한 오픈소스 공급망 공격

xz-utils 백도어 (CVE-2024-3094)

"Jia Tan"이라는 인물이 2년 넘게 xz-utils 프로젝트에 정상적으로 기여하며 신뢰를 쌓고 메인테이너 권한까지 얻은 뒤, 2023년 12월 배포판(v5.6.0)에 백도어를 몰래 심었습니다. 이 백도어는 sshd가 쓰는 OpenSSL 함수(RSA_public_decrypt)를 가로채 특정 개인키를 가진 공격자에게 원격 코드 실행을 허용합니다. GitHub 저장소가 아니라 배포 버전에만 숨겨져 있어서 코드 리뷰로는 못 찾았습니다.

발견 경위도 극적입니다 — 마이크로소프트 엔지니어가 PostgreSQL 성능 이슈를 디버깅하다가 "SSH 로그인이 0.5초 더 걸린다"는 사소한 이상을 알아채면서 우연히 드러났습니다. 감염된 배포판: Fedora 40 베타, Debian unstable, Kali Linux, 특정 기간의 Arch Linux 이미지. (Ubuntu, Amazon Linux는 영향 없었음)

왜 중요한가. 자동 스캔으로는 절대 못 잡는 유형입니다. "메인테이너 자체가 위협"이라는 점에서, 우리가 다루는 "의존성 유지보수 상태"(마지막 업데이트, 메인테이너 수 등) 체크가 왜 위험 신호가 되는지 보여주는 최고의 사례입니다.

사례 3 · AI 특화 신흥 위협

AI 모델 파일 자체의 악성코드

공개 모델 레지스트리(Hugging Face 등)에서 포이즈닝된 모델 파일을 로드하면 임의 코드가 실행되는 사례들이 발견됐습니다. 조직의 53%가 모델을 공개 레지스트리에서 직접 받아쓰는데, 검증 없이 받으면 그대로 침투 경로가 됩니다. 우리 프로젝트 범위(PyPI 패키지)를 넘어서지만, "AI 에이전트 생태계 전체가 공급망 공격의 신흥 표적"이라는 배경 논리를 뒷받침합니다.

FAQ

Q. SBOM이랑 requirements.txt랑 뭐가 다른가요?
requirements.txt는 "설치할 목록"(사람이 직접 관리), SBOM은 "실제로 뭐가 들어있는지 기계가 읽을 수 있게 표준화한 명세서"(도구가 생성, 해시·라이선스·취약점 정보까지 포함). SBOM이 requirements.txt를 포함하는 상위 개념입니다.
Q. SCA, SBOM, 우리 프로젝트(ASM) 관계가 뭔가요?
SBOM(부품 목록 만들기) → SCA(그 목록에서 알려진 문제 찾기) → 우리 프로젝트는 여기에 "그 문제가 AI 에이전트의 실제 권한과 연결되는가"라는 한 단계를 더 얹는 것입니다.
Q. 왜 requirements.txt 파싱이랑 pipreqs 임포트 스캔을 둘 다 해야 하나요?
requirements.txt는 사람이 쓴 것이라 실제 코드와 다를 수 있습니다. 두 결과를 pipreqs --diff로 비교하면 "선언은 안 됐지만 실제로 쓰이는" 숨은 의존성까지 잡아낼 수 있습니다 — 자산을 빠짐없이 식별해야 하는 이유입니다.
Q. xz-utils 사례는 자동화 도구로 막을 수 있었나요?
못 막았습니다. 코드가 GitHub엔 없고 배포 버전에만 있었고, 정상적으로 신뢰를 쌓은 메인테이너가 심은 것이라 자동 스캐너의 패턴 탐지로는 걸러지지 않았습니다. 이게 "규칙 기반 탐지의 한계"이고, ML 이상탐지를 추가하는 이유와 연결됩니다(다만 ML도 이런 극단적 사례까지 잡는다고 보장할 순 없다는 건 솔직히 인지해야 함).
Q. 공격경로 분석(Attack Path Engine)이 왜 단순 취약점 스캔보다 나은가요?
스캔은 수천 개의 개별 findings를 쏟아내지만 뭐가 진짜 위험한지 안 알려줍니다. 공격경로 분석은 "여러 개의 낮은 위험이 사슬처럼 연결돼야만 진짜 위험한 경로가 된다"는 걸 보여줘서, 대응 우선순위를 정확하게 잡아줍니다.
