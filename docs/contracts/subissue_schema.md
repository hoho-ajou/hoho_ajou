# 하위 이슈(Sub-issue) 공통 스키마

**하위 이슈는 각 담당자가 직접 만듭니다 (총괄이 대신 만들지 않음).** 다만 그대로 구현할 수 있을 만큼 구체적이어야 하므로, 아래 스키마를 담당자 전원이 동일하게 따릅니다. `docs/roles/rX-*.md`(본인 역할 상위 이슈)의 "범위" 항목 하나가 보통 하위 이슈 1~3개로 쪼개집니다.

이슈 구조는 3단입니다: 전체 Epic(#1) → 역할 상위 이슈(R1~R4, `docs/roles/*.md`) → 하위 이슈(지금 이 문서). 하위 이슈는 **역할 상위 이슈**를 참조합니다 — Epic(#1)을 직접 참조하지 않습니다.

## 필수 섹션 (순서 고정)

```markdown
# [<모듈>] <구체적 작업 — 동사로 끝나는 한 문장>

## 상위 이슈
Relates to #<역할 상위 이슈 번호> (R1~R4 중 본인 역할)

## 작업 내용
(어떤 파일/함수/클래스를 만들거나 고치는지 구체적으로. "파서 구현" 대신
"`collector/parsers/requirements_txt.py`에 `parse(path: str) -> list[Dependency]` 구현" 수준)

## 입력/출력 예시
(최소 1개의 구체적인 입력값 → 출력값 쌍. 표나 JSON 스니펫으로.
관련 있으면 `schemas/*.schema.json`의 어느 필드를 채우는지 명시)

## 완료조건 (Acceptance Criteria)
- [ ] (테스트 가능한 조건. 가능하면 실제 테스트 케이스 이름/커맨드까지)

## 엣지케이스
(비어있는 입력, 존재하지 않는 패키지, 네트워크 실패 등 — 표로 "상황 → 기대 동작")

## 참고자료
(해당 모듈 `docs/design/0X-*.md`의 관련 절 번호, study_week1 자료)
```

## 필드 규칙

| 필드 | 규칙 |
|---|---|
| 제목 | `[<모듈명>]` 접두사. 브랜치명은 `CONTRIBUTING.md` 규칙대로 `<모듈>/<이슈번호>-<설명>` |
| 작업 내용 | 파일 경로와 함수 시그니처까지 — 구현자가 "어디에 뭘 만들지" 추측하지 않게 |
| 입력/출력 예시 | 산문 설명만으로 끝내지 않음. 실제 값 예시 필수 (누가 봐도 모호하지 않게) |
| 엣지케이스 | 최소 2개. 설계 문서의 "3. 에러 처리 원칙"(`01-collector.md` 등)에 이미 정의된 원칙을 재확인 |
| 크기 | 하위 이슈 하나가 리뷰 가능한 PR 1개 분량을 넘지 않도록 쪼갬 (기준: 파일 1~3개, 리뷰 시간 30분 이내) |

## GitHub Issue로 옮길 때

- 제목에 `[모듈명]` 접두사만 유지 (라벨은 쓰지 않음 — `CONTRIBUTING.md` 참고)
- `Depends on #`으로 선행 이슈 명시 (병렬 작업 시 충돌 방지)
- 본인 역할 상위 이슈(R1~R4)에 체크리스트 항목으로 연결 (GitHub의 tasklist 문법 사용 가능)
